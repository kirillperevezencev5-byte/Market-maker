MARKETPILOT — SECURITY & CORE 2.0

Полный аудит и усиление безопасности, прав доступа и архитектуры платформы

Ты работаешь над MarketPilot — SaaS-платформой для управления Telegram-сообществами. Твоя задача — провести глубокий технический аудит существующего проекта, выявить слабые места и довести фундаментальные механизмы безопасности до production-ready состояния.

Главный принцип: не переписывай проект с нуля. Развивай существующую архитектуру, сохраняя рабочие функции, совместимость и текущую структуру проекта.

Работай самостоятельно, последовательно и итеративно. Не ограничивайся рекомендациями — вноси изменения в код, запускай тесты, исправляй ошибки и проверяй результат.

1. ПОЛНЫЙ АУДИТ ТЕКУЩЕГО СОСТОЯНИЯ

Перед внесением изменений:

1. Изучи всю структуру проекта.
2. Определи используемый стек, архитектуру Backend и Frontend.
3. Изучи систему авторизации и управления сессиями.
4. Проверь механизм подключения Telegram-сообществ.
5. Изучи Workspace, пользователей, роли и разрешения.
6. Проверь тарифную систему и ограничения подписок.
7. Изучи API endpoints и middleware.
8. Проверь работу платежей и подтверждение оплаты.
9. Изучи существующий Audit Log.
10. Проверь конфигурацию Docker, переменные окружения и production-настройки.

Составь внутреннюю карту зависимостей между основными компонентами.

Не создавай дублирующие механизмы, если аналогичные уже существуют. Улучшай текущие реализации.

2. WORKSPACE ISOLATION — ИЗОЛЯЦИЯ ДАННЫХ

Это один из самых важных компонентов MarketPilot.

Каждый пользователь должен иметь доступ только к тем данным, на которые у него есть соответствующие права.

Реализуй или усиль:

* Строгую изоляцию Workspace.
* Проверку принадлежности сообщества Workspace.
* Проверку владельца и участника Workspace.
* Изоляцию публикаций, аналитики, настроек и автоматизаций.
* Защиту от доступа к чужим объектам через подмену ID.
* Проверку прав при каждом критическом API-запросе.
* Корректную обработку ситуаций, когда пользователь удалён из Workspace.

Проверь возможность IDOR/BOLA-атак.

Важно: недостаточно скрыть чужие данные во Frontend. Все проверки должны выполняться на сервере.

3. RBAC 2.0 — РОЛИ И ПРАВА ДОСТУПА

Проведи аудит текущей системы ролей.

Предусмотри следующие роли, если они отсутствуют или реализованы неполно:

* Owner — полный контроль над Workspace.
* Admin — управление сообществами и участниками в рамках разрешений.
* Manager — управление публикациями и рабочими процессами.
* Moderator — модерация контента и участников.
* Analyst — просмотр аналитики без права изменения настроек.
* Viewer — доступ только для чтения.

Для каждой роли должна существовать чёткая матрица разрешений.

Требования:

* Серверная проверка разрешений.
* Невозможность повысить собственные права.
* Защита от изменения роли через прямой API-запрос.
* Проверка прав при выполнении фоновых задач.
* Немедленное прекращение доступа после удаления участника.
* Отдельная проверка критических действий Owner.

Не допускай ситуации, когда Frontend скрывает кнопку, но Backend всё равно разрешает действие.

4. SERVER-SIDE SUBSCRIPTION ENFORCEMENT

Проведи аудит тарифной системы.

Все тарифные ограничения должны проверяться на Backend.

Проверь:

* Количество подключённых сообществ.
* Количество публикаций.
* Лимиты AI-запросов.
* Доступность AI-функций.
* Доступность автоматизаций.
* Ограничения команд и участников.
* Доступность аналитики.
* Ограничения Marketplace.
* Срок действия подписки.
* Состояние оплаты.
* Переход между тарифами.

Реализуй единый механизм проверки тарифных возможностей.

Пример логики:

Пользователь → Workspace → Активная подписка → Проверка тарифа → Проверка лимита → Разрешение или отказ.

Требования:

* Нельзя обойти лимиты прямым API-запросом.
* Нельзя получить PRO-функции через изменение Frontend.
* Нельзя подменить тариф через пользовательские данные.
* Лимиты должны корректно обновляться.
* Истёкшая подписка должна обрабатываться автоматически.
* При отказе API должен возвращать понятную ошибку.

Не допускай потери данных при понижении тарифа. Существующие ресурсы должны обрабатываться согласно заранее определённой политике ограничений.

5. AUTHENTICATION & SESSION SECURITY

Проведи аудит авторизации.

Проверь:

* Валидацию Telegram Init Data.
* Проверку подписи Telegram.
* Проверку времени формирования Init Data.
* Защиту от повторного использования устаревших данных.
* Создание и обновление сессий.
* Срок действия токенов.
* Отзыв сессий.
* Проверку пользователя на каждом защищённом запросе.
* Защиту от подмены Telegram ID.
* Безопасную обработку выхода из аккаунта.

Если используется собственная система JWT или сессий, проверь её криптографическую и архитектурную корректность.

Не доверяй Telegram ID, переданному клиентом без серверной проверки.

6. API SECURITY

Проведи аудит всех API endpoints.

Проверь:

* Authentication.
* Authorization.
* Input Validation.
* Rate Limiting.
* SQL Injection.
* XSS.
* CSRF — если применимо к используемой архитектуре.
* Mass Assignment.
* Небезопасную десериализацию.
* Утечку внутренних ошибок.
* Возможность обхода middleware.
* Проверку типов и размеров входящих данных.

Добавь централизованную обработку ошибок.

Не возвращай пользователю Stack Trace, внутренние пути файлов, секреты или конфиденциальные данные.

Для чувствительных endpoints предусмотрите отдельные ограничения частоты запросов.

7. TELEGRAM BOT SECURITY

Проверь взаимодействие MarketPilot с Telegram Bot API.

Особое внимание:

* Проверке входящих webhook-запросов.
* Проверке секретного токена webhook.
* Безопасному хранению Bot Token.
* Защите от повторной обработки Update.
* Проверке прав бота в сообществе.
* Проверке принадлежности сообщества Workspace.
* Корректной обработке удаления бота из сообщества.
* Безопасности фоновых задач.

Нельзя выполнять административные действия в сообществе без проверки полномочий пользователя и доступных прав бота.

8. PAYMENT SECURITY

Проведи аудит YooKassa и существующей платёжной архитектуры.

Проверь:

* Подлинность уведомлений.
* Проверку статуса платежа через доверенный источник.
* Защиту от повторной обработки webhook.
* Идемпотентность операций.
* Невозможность самостоятельно активировать подписку через Frontend.
* Корректность возвратов и отмен.
* Синхронизацию состояния платежа и подписки.
* Защиту от повторного начисления преимуществ.

Статус оплаты должен определяться исключительно серверной логикой.

Не изменяй реальные настройки платежей без необходимости.

9. AUDIT LOG 2.0

Усиль журналирование действий.

Необходимо фиксировать:

* Входы и выходы.
* Создание и удаление Workspace.
* Добавление и удаление участников.
* Изменение ролей.
* Изменение тарифов.
* Подключение и отключение сообществ.
* Изменение настроек.
* Публикации и удаления контента.
* Запуск и изменение автоматизаций.
* Изменения платёжного состояния.
* Критические ошибки безопасности.

Каждая запись должна по возможности содержать:

* Пользователя.
* Workspace.
* Тип действия.
* Объект изменения.
* Время.
* Результат операции.

Не записывай пароли, токены, секретные ключи и другие чувствительные данные.

Обычный пользователь не должен иметь возможности изменять или удалять системные записи аудита.

10. SECRETS & ENVIRONMENT SECURITY

Проверь:

* Отсутствие реальных ключей в Git.
* Исключение .env из репозитория.
* Наличие безопасного .env.example.
* Отсутствие секретов в логах.
* Безопасную конфигурацию Docker.
* Отсутствие debug-режима в production.
* Корректную обработку отсутствующих переменных окружения.

Если обнаружены реальные секреты, не публикуй их в отчёте. Укажи, какие именно типы ключей необходимо заменить.

Не выводи значения API-ключей в терминал и итоговый отчёт.

11. RATE LIMITING & ABUSE PROTECTION

Добавь или улучши ограничения:

* На авторизацию.
* На API-запросы.
* На AI-запросы.
* На создание публикаций.
* На изменение настроек.
* На критические операции.
* На платёжные операции.

Предусмотри защиту от массовых запросов, спама и злоупотребления API.

Учитывай многопользовательскую архитектуру: лимиты должны корректно разделяться по пользователям, Workspace и отдельным операциям.

12. TESTING

Создай полноценный набор тестов.

Обязательно протестируй:

1. Пользователь A не может получить данные Workspace пользователя B.
2. Пользователь не может изменить чужую публикацию.
3. Moderator не может выполнять действия Owner.
4. Viewer не может изменять настройки.
5. Пользователь не может самостоятельно повысить тариф.
6. Пользователь не может обойти лимиты через API.
7. Истёкшая подписка корректно ограничивает функции.
8. Нельзя активировать подписку поддельным запросом.
9. Повторный webhook не приводит к повторной обработке платежа.
10. Удалённый участник теряет доступ.
11. Невалидный Telegram Init Data отклоняется.
12. Устаревшая сессия не даёт доступ.
13. Нельзя получить чужие данные через подмену ID.
14. Фоновые задачи проверяют актуальные права.
15. Секретные данные не попадают в логи.

Добавь интеграционные тесты и негативные сценарии.

Не ограничивайся тестированием успешных запросов.

13. FRONTEND

Проверь пользовательский интерфейс:

* Корректное отображение доступных функций.
* Отсутствие функций, недоступных по тарифу.
* Понятные сообщения об ограничениях.
* Корректная обработка 401, 403 и 429.
* Отсутствие утечки внутренних ошибок.
* Синхронизация интерфейса с актуальными правами пользователя.

Frontend должен отражать реальные серверные разрешения, но никогда не заменять серверную проверку.

14. ПРОИЗВОДИТЕЛЬНОСТЬ И СОВМЕСТИМОСТЬ

Проверь, чтобы новые механизмы:

* Не создавали лишние запросы к БД.
* Не замедляли основные сценарии.
* Не нарушали работу Scheduler.
* Не ломали AI Assistant.
* Не нарушали работу Marketplace.
* Не ломали платежи.
* Не создавали конфликтов с существующими Background Jobs.

При необходимости добавь индексы БД и оптимизируй запросы.

Итерация 2: Workspace Isolation и защита данных.

Итерация 3: RBAC и серверная проверка разрешений.

* Проверь изменённые файлы.
* Запусти соответствующие тесты.

* Убедись, что существующие функции продолжают работать.

Не переходи к следующей итерации, пока текущая не находится в стабильном состоянии.

Если обнаружишь критическую проблему, сначала устрани её.

16. ФИНАЛЬНЫЕ КРИТЕРИИ ГОТОВНОСТИ

Работа считается завершённой, когда:

* Workspace изолированы на серверном уровне.
* RBAC работает на Backend.
* Тарифные ограничения нельзя обойти через API.
* Telegram Authentication проходит полноценную проверку.
* Платёжные операции защищены от повторной обработки.
* Критические действия журналируются.
* Секреты не раскрываются.
* API защищены от основных распространённых атак.
* Rate Limiting работает.
* Интеграционные и негативные тесты проходят.
* Существующие функции MarketPilot не сломаны.

Не заявляй о production-ready, если тесты не запускались или реальные сценарии не проверены.
