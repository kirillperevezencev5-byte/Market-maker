MARKETPILOT — USER AUTOPOSTING 2.0

Полноценная система подачи, модерации, согласования и автоматической публикации объявлений

Ты работаешь над MarketPilot — SaaS-платформой для управления Telegram-сообществами.

Твоя задача — разработать полноценную систему User Autoposting 2.0, позволяющую пользователям размещать объявления в подключённых Telegram-сообществах через MarketPilot, а владельцам сообществ — контролировать, модерировать и монетизировать публикации.

Главная цель: создать удобный и надёжный механизм, в котором весь цикл размещения объявления проходит внутри MarketPilot: от подачи пользователем до публикации в Telegram.

Не создавай отдельный проект и не переписывай существующую архитектуру. Сначала изучи текущую реализацию, затем развивай её.

5. Проверь текущую систему тарифов.

Определи, какие механизмы можно переиспользовать.

2. USER SUBMISSION — ПОДАЧА ОБЪЯВЛЕНИЙ

Создай удобный интерфейс подачи объявления.

Пользователь должен иметь возможность:

* Выбрать Telegram-сообщество.
* Указать заголовок объявления.
* Написать текст.
* Добавить фотографии.
* Добавить ссылки.
* Выбрать категорию.
* Указать контактную информацию.
* Посмотреть предварительный просмотр.
* Отправить объявление на модерацию.

Предусмотри поддержку нескольких фотографий и корректное отображение медиа.

Добавь проверку:

* Максимальной длины текста.
* Количества фотографий.
* Форматов файлов.
* Размеров загружаемых файлов.
* Допустимых ссылок.
* Обязательных полей.
* Доступности выбранного сообщества.

Количество фотографий и другие ограничения должны определяться конфигурацией и тарифом сообщества.

Пользователь должен видеть понятные ошибки, а не технические сообщения.

3. MODERATION QUEUE — ОЧЕРЕДЬ МОДЕРАЦИИ

Создай отдельный интерфейс модерации для владельцев и сотрудников сообществ.

Все новые объявления должны попадать в очередь модерации, если для сообщества включена предварительная проверка.

Карточка объявления должна содержать:

* Заголовок.
* Текст.
* Фотографии.
* Имя автора или его отображаемый идентификатор.
* Дату подачи.
* Название сообщества.
* Категорию.
* Статус.
* Историю предыдущих решений.

Модератор должен иметь возможность:

* Одобрить объявление.
* Отклонить объявление.
* Отправить на доработку.
* Изменить текст перед публикацией, если его роль это разрешает.
* Оставить комментарий.
* Просмотреть историю действий.

При отклонении обязательно должна быть возможность указать причину.

При отправке на доработку пользователь должен получить объяснение, что именно необходимо исправить.

4. STATUS SYSTEM — СИСТЕМА СТАТУСОВ

Реализуй единую систему статусов.

Предусмотри следующие состояния:

* Draft — черновик.
* Submitted — отправлено.
* Pending Moderation — ожидает проверки.
* Revision Required — требуется доработка.
* Approved — одобрено.
* Rejected — отклонено.
* Scheduled — запланировано.
* Publishing — публикация выполняется.
* Published — опубликовано.
* Failed — ошибка публикации.
* Cancelled — отменено.

Реализуй корректные переходы между состояниями.

Запрещай некорректные переходы. Например, нельзя опубликовать отклонённое объявление без повторного согласования.

Все изменения статусов должны фиксироваться в истории.

5. AUTOMATIC PUBLISHING — АВТОМАТИЧЕСКАЯ ПУБЛИКАЦИЯ

После одобрения объявления система должна автоматически подготовить его к публикации.

Поддержи два сценария:

Сценарий A — немедленная публикация

После одобрения объявление автоматически отправляется в выбранное Telegram-сообщество.

Сценарий B — отложенная публикация

Модератор или владелец выбирает дату и время публикации.

Scheduler должен самостоятельно выполнить публикацию в заданное время.

Обязательно реализуй:

* Проверку актуальности статуса перед публикацией.
* Проверку прав бота.
* Проверку подключения сообщества.
* Проверку лимитов.
* Идемпотентность публикации.
* Защиту от повторной отправки.
* Обработку ошибок Telegram API.
* Повторные попытки при временных сбоях.
* Логирование результата.

Повторная попытка не должна приводить к дублированию объявления в Telegram.

Если публикация не удалась, объявление должно перейти в Failed с понятным объяснением.

6. COMMUNITY SETTINGS — НАСТРОЙКИ ПРИЁМА ОБЪЯВЛЕНИЙ

Добавь настройки для каждого сообщества.

Владелец должен иметь возможность:

* Включить или отключить приём объявлений.
* Включить обязательную модерацию.
* Разрешить автоматическую публикацию после одобрения.
* Включить отложенную публикацию.
* Установить максимальное количество объявлений.
* Установить ограничения по фотографиям.
* Настроить минимальный интервал между публикациями.
* Установить правила оформления.
* Настроить категории объявлений.
* Установить стоимость размещения, если включена монетизация.

Настройки должны быть независимыми для каждого сообщества.

Проверяй разрешения пользователя перед изменением настроек.

7. USER CABINET — ЛИЧНЫЙ КАБИНЕТ АВТОРА

Создай страницу, где пользователь сможет отслеживать свои объявления.

Предусмотри:

* Все объявления.
* Ожидающие модерации.
* Одобренные.
* Требующие доработки.
* Отклонённые.
* Запланированные.
* Опубликованные.

Пользователь должен видеть историю каждого объявления.

Добавь возможность:

* Редактировать черновик.
* Исправить объявление после возврата на доработку.
* Отменить ещё не опубликованное объявление.
* Повторно отправить исправленное объявление.
* Просмотреть опубликованный результат.

Не разрешай изменять опубликованное объявление так, чтобы история переставала соответствовать фактическому содержимому.

8. NOTIFICATIONS — УВЕДОМЛЕНИЯ

Добавь систему уведомлений.

Автор должен получать уведомления о:

* Принятии объявления.
* Отклонении.
* Необходимости доработки.
* Успешной публикации.
* Ошибке публикации.
* Отмене публикации.

Модераторы должны получать уведомления о новых объявлениях, ожидающих проверки.

Предусмотри уведомления через Telegram-бота и интерфейс MarketPilot, используя существующую архитектуру уведомлений.

Не отправляй дублирующиеся уведомления при повторной обработке одного события.

9. ANTI-SPAM & MODERATION RULES

Добавь базовую защиту от злоупотреблений.

Проверь:

* Частоту подачи объявлений.
* Повторяющиеся объявления.
* Повторяющиеся ссылки.
* Массовую отправку одинакового контента.
* Подозрительные URL.
* Запрещённые слова и выражения.
* Попытки обойти ограничения через редактирование текста.
* Чрезмерное количество вложений.

Добавь настраиваемые правила модерации.

Не блокируй пользователей автоматически только на основании одного слабого признака.

Предусмотри возможность ручной проверки подозрительных объявлений.

10. MONETIZATION PREPARATION — ПОДГОТОВКА К МОНЕТИЗАЦИИ

Подготовь архитектуру к платным объявлениям.

Важно: на этом этапе не нужно создавать полностью новую платёжную систему. Используй существующую YooKassa-интеграцию.

Предусмотри:

* Бесплатные объявления.
* Платные объявления.
* Разные цены для разных сообществ.
* Возможность платного закрепления.
* Возможность дополнительных опций размещения.
* Статусы оплаты.
* Связь платежа с конкретным объявлением.
* Проверку оплаты перед публикацией платного объявления.

Статус оплаты должен подтверждаться исключительно сервером.

Не допускай публикации платного объявления до подтверждения оплаты.

Не допускай повторного списания при повторной обработке события.

Если платёжная интеграция уже поддерживает необходимые сценарии, переиспользуй её.

11. OWNER DASHBOARD — ПАНЕЛЬ ВЛАДЕЛЬЦА

Предусмотри фильтрацию по датам и сообществам.

Показатели должны рассчитываться на основе реальных данных БД.

Не используй искусственные или демонстрационные значения в рабочем интерфейсе.
